# Every routes — 全体概要と共通モデル

## 1. これは何か

1日の予定・生活ルーティンを管理する **Android アプリ（Every routes）** と、その情報を複数端末・外部アプリ間で共有するための **共有サーバー（Every routes server）** をあわせて開発する。

一般的なカレンダーが「日付ごとに個別の予定を置く」ものであるのに対し、Every routes は **「1日の過ごし方そのもの」をプロファイル（ルーティンプロファイル）として登録し、それを曜日・祝日条件で繰り返し適用する** ことを中心に据える。

- 「平日」「休日」などのルーティンプロファイルを作り、繰り返し条件で日々に割り当てる
- Google Tasks や AI エージェント（OpenClaw 等）から入ってくる一時的なタスクも統合し、「その日の行動」としてまとめて表示する
- 共有サーバーを介して、機種変更・複数端末でも同じルーティンを引き継げるようにする
- サーバーは Android 専用ではなく、外部アプリ／エージェントも読み書きできる **共通ハブ** とする

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| ルーティンプロファイル | 「平日」「休日」など、1日の流れを表す単位。時間帯ブロックと繰り返し条件を持つ |
| 時間帯ブロック | ルーティン内の1件の予定。`07:00〜07:30 起床・準備` のように **時間範囲** を持つ |
| タスク | `15:00` のように **特定時刻**（または期日のみ）に存在する一時的な予定。Google Tasks / エージェント / 手動入力が発生源 |
| ルーティンアドレス | 共有ルーティンに割り当てられる 256bit 相当のランダム識別子。名前と独立で、原則不変。同期の突き合わせキー |
| 共有サーバー / ハブ | Every routes server。ルーティン・タスクを端末／外部アプリ間で受け渡す中継点 |
| 今日ビュー | その日のルーティン（時間帯ブロック）とタスクを時系列に統合した表示 |

## 3. 全体構成

```
                 ┌──────────────────────────┐
                 │   Every routes server    │
                 │  (Mac / Linux, 軽量)     │
                 │  ルーティン / タスクを保持 │
                 └──────────┬───────────────┘
             LAN / VPN 経由の HTTP(S)
      ┌───────────────┼───────────────┬─────────────────┐
      │               │               │                 │
┌───────────┐   ┌───────────┐   ┌────────────┐    ┌──────────────┐
│ Android A │   │ Android B │   │  OpenClaw  │    │ 他の外部アプリ │
│（端末）    │   │（端末）    │   │ / AI エージェント │  / スクリプト   │
└───────────┘   └───────────┘   └────────────┘    └──────────────┘
      │
  Google Tasks API（各端末が個別に取得）
```

- 端末とサーバーの接続前提は **家庭内 LAN、または VPN で同一ネットワークに入った状態**。インターネット常時公開は想定しない。
- Android アプリは端末外の既存 VPN（`DIRECT`）に加え、アプリ自身が WireGuard トンネルを開始する **App-only VPN（`APP_ONLY_WIREGUARD`）** を選択できる（既定 OFF）。詳細は [`04-app-wireguard-vpn.md`](04-app-wireguard-vpn.md)。
- サーバーはクラウドサービスというより「複数端末・複数アプリのための共有バッファ」。

## 4. 共通データモデル

端末・サーバー・外部アプリで同じ意味を持つように、以下を共通形式（JSON）とする。時刻の扱いは §5 を参照。

### 4.1 ルーティンプロファイル

```json
{
  "schemaVersion": 1,
  "routineAddress": "rt_9f2c4b...（64桁の16進 = 256bit）",
  "name": "平日",
  "lastModified": "2026-09-10T08:12:33Z",
  "recurrence": {
    "daysOfWeek": ["MON", "TUE", "WED", "THU", "FRI"],
    "holiday": "exclude"
  },
  "blocks": [
    { "id": "blk_1", "start": "07:00", "end": "07:30", "title": "起床・準備", "note": "" },
    { "id": "blk_2", "start": "09:00", "end": "09:30", "title": "通勤",       "note": "" },
    { "id": "blk_3", "start": "12:00", "end": "13:00", "title": "昼食",       "note": "" }
  ]
}
```

| フィールド | 説明 |
| --- | --- |
| `schemaVersion` | 形式のバージョン。将来の互換維持のため |
| `routineAddress` | 共有時に割り当てる 256bit ランダム ID（16進 64桁、接頭辞 `rt_` 任意）。**一度割り当てたら変更しない**。未共有ローカルプロファイルでは空でよい |
| `name` | 表示名。重複可。同期の基準には使わない |
| `lastModified` | 最終変更日時（UTC, RFC3339）。同一 `routineAddress` の新旧判定に使う |
| `recurrence.daysOfWeek` | 実行する曜日（`MON`〜`SUN`）。空 = 曜日では実行しない |
| `recurrence.holiday` | 祝日の扱い。`exclude`（祝日は実行しない） / `include`（曜日条件に加え祝日も実行） / `only`（祝日のみ実行） |
| `blocks[]` | 時間帯ブロックの配列。`start`/`end` は端末ローカル時刻の "HH:MM"（24h）。`end` が `start` より前の場合は翌日跨ぎ |
| `blocks[].id` | プロファイル内で一意。並び順は配列順 |

「平日ルーティン」= `daysOfWeek: [MON..FRI]` + `holiday: exclude`、
「休日ルーティン」= `daysOfWeek: [SAT, SUN]` + `holiday: include` のように表現する。

### 4.2 タスク

```json
{
  "schemaVersion": 1,
  "id": "tsk_3a91...",
  "source": "google_tasks",
  "externalId": "MTIzNDU2Nzg5...",
  "title": "歯医者",
  "at": "2026-09-11T15:00:00+09:00",
  "allDay": false,
  "status": "needsAction",
  "lastModified": "2026-09-10T09:00:00Z",
  "deleted": false
}
```

| フィールド | 説明 |
| --- | --- |
| `id` | サーバー／端末をまたいで一意なタスク ID |
| `source` | `google_tasks` / `agent`（OpenClaw 等）/ `manual`（端末手入力） |
| `externalId` | 発生源側の ID（Google Tasks のタスク ID 等）。重複取り込み防止に使う |
| `title` | タスク名 |
| `at` | 予定時刻（タイムゾーン付き RFC3339）。`allDay: true` のときは日付部分のみ意味を持つ |
| `allDay` | 時刻が定まらないタスク（期日のみ）を表す |
| `status` | `needsAction` / `completed` |
| `lastModified` | 最終変更日時（UTC）。新旧判定に使う |
| `deleted` | 論理削除フラグ（tombstone）。物理削除はしない |

> ルーティンは「時間範囲を持つ予定」、タスクは「特定時刻（または期日のみ）の予定」という区別を維持する。

### 4.3 今日ビューの組み立て（各端末で計算）

指定日 `D`（端末のタイムゾーン）について:

1. 全ルーティンプロファイルから、`D` に該当するものを選ぶ
   - `D` の曜日が `daysOfWeek` に含まれる、または
   - `D` が祝日で `holiday` が `include` / `only`、かつ
   - `D` が祝日で `holiday` が `exclude` の場合は除外
2. 該当ルーティンの `blocks` を時系列に展開（跨ぎブロックは日付境界で分割して表示）
3. `at` が `D`（端末TZ）に入るタスクを、時刻順に同じタイムラインへマージ
4. 現在時刻を基準に「進行中ブロック」「次のブロック」「次のタスク」を決定 → アプリ本体とウィジェットで共用

祝日判定のカレンダーはサーバー設定（地域）と端末設定を持ち、既定は日本（`JP`）。

## 5. 時刻・タイムゾーンの扱い

- `lastModified` は必ず **UTC**。端末の時計ずれを避けるため、サーバーへ書き込んだ結果のレスポンスに含まれる `lastModified` を正として端末が採用する。
- 時間帯ブロックの `start`/`end` は「その日のローカル時刻」を意味する壁時計値（"HH:MM"）で持ち、特定タイムゾーンには紐付けない。
- タスクの `at` はタイムゾーン付きの絶対時刻で持つ。

## 6. 同期モデル（共通ルール）

### 6.1 基準は「ルーティンアドレス」

- ルーティンの同期は **名前ではなく `routineAddress` で突き合わせる**。
- 同名「平日」が複数あっても、アドレスが違えば別ルーティン。
- 端末はインポート時に **内容と一緒に `routineAddress` も保存** し、以後その端末の同じアドレスのルーティンとして扱う。

### 6.2 競合解決（last-write-wins）

同一 `routineAddress`（またはタスク `id`）のデータを比較したとき:

1. `lastModified` が新しい方を採用し、古い側を上書きする。
2. `lastModified` が同一なら内容ハッシュを比較し、一致すれば何もしない。不一致ならサーバー側を正とする（端末は取り込み直す）。
3. サーバーは、受け取った内容の `lastModified` が保持中のものより古い場合、書き込みを拒否し現行データを返す（端末は `force` 指定で明示上書き可能）。

### 6.3 同期の流れ（例：端末A編集 → 端末B反映）

```
端末A: ルーティン編集（lastModified 更新）
  └─ PUT /routines/{addr}  ──▶  サーバー: 同じ addr のデータを更新
端末B: 定期同期
  └─ GET /routines 一覧 → 自分が持つ addr の lastModified を比較
       サーバーが新しい → GET /routines/{addr} で取得し端末B側を上書き
```

- サーバーにしか存在しないアドレス（他人／他端末が新規追加したルーティン）は **自動では取り込まない**。インポート画面に候補として並べ、ユーザーが選んで初めて端末に入る。
- タスクは日付範囲・`since` 付きで取得し、`id` 単位で upsert、`deleted` を反映する。
